## 2. ⚠️ حقيقة يجب معرفتها قبل البدء

```
فيزياء ✅ 7 وحدات · 41 درساً      عربي   ✅ 1 وحدة · 11 درساً
كيمياء ✅ 6 وحدات · 59 درساً      انجليزي ✅ 1 وحدة · 17 درساً
رياضيات ✅ 5 فروع · 64 درساً
احياء  ❌ **لا دروس إطلاقاً** — صفحات فقط (7 وحدات · 162 صفحة)
```

**الأحياء لا تدعم «اختر الدرس»** لأن محتواها صفحات لا دروس ([ADR-011](08-decisions.md)).
**الحل المقترح:** الأحياء تختار **الوحدة فقط** (والأسئلة تُولَّد من صفحاتها)، وبقية المواد وحدة → دروس. القيد يظهر في الواجهة تلقائياً من `capabilities` بلا استثناءات مكتوبة يدوياً.

## 3. الوزاري يختفي من الصفين الأول والثاني ✅

قرارك: الوزاري امتحان وطني للثالث فقط، فلا معنى له في الأول والثاني.

**التنفيذ الحالي يخدمنا:** الباك اند **أصلاً** يرجع `[]` لسنوات الوزاري لغير الثالث ([26](26-grade-isolation.md)). ما ينقص هو إخفاء الوضع نفسه.

```
Curriculum.modesFor(subject)  →  modesFor(grade, track, subject, caps)
   شرح · تلخيص · سؤال            ← دائماً (الرياضيات بلا تلخيص)
   وزاري                        ← فقط إن وُجد بنك أسئلة لهذا الصف/المسار
   اختبارات 🧠                   ← فقط إن وُجد محتوى دروس/صفحات
```

**مصدر القرار = `/content/capabilities`** (يُضاف إليه `exams.available` و`quiz.available`)، لا شروط مكتوبة في الواجهة. النتيجة العملية اليوم:

| الصف | الأوضاع الظاهرة |
|---|---|
| الثالث علمي | شرح · تلخيص · سؤال · **وزاري** · **اختبارات** |
| الأول · الثاني (علمي وأدبي) | شرح · تلخيص · سؤال · **اختبارات** (وتظهر «قيد الإضافة» حتى يُضاف محتواها) |

> ❓ **قرار مطلوب:** هل يرى الثالث الوضعين معاً (5 شرائح) أم نستبدل الوزاري بالاختبارات عنده أيضاً؟ **توصيتي: الاثنان** — الوزاري أسئلة حقيقية سابقة، والاختبارات تدريب مولَّد؛ وظيفتان مختلفتان.

## 5. الباك اند — `POST /quiz/generate` 🆕

```jsonc
// الطلب
{ "grade": 3, "track": "علمي", "subject": "فيزياء",
  "unit": "الفيزياء الذرية",
  "lessons": ["نظرية بوهر", "فيزياء الذرة"],   // حتى 3 — فارغة = الوحدة كلها
  "count": 10 }                                  // 5 | 10 | 15

// الرد
{ "questions": [
    { "q": "…", "options": ["…","…","…","…"], "correct_index": 2,
      "topic": "مستويات الطاقة", "lesson": "نظرية بوهر" } ],
  "generated": 10, "subject": "فيزياء", "unit": "…" }
```

| الخطوة | التفصيل |
|---|---|
| 1. التوثيق | نفس بوابة `/ask` (توكن Firebase) |
| 2. الحصة | حصة **خفيفة** (`light`) لا حصة السؤال — نداء واحد لكل اختبار |
| 3. المنهج | `is_valid_subject(grade, track, subject)` وإلا 400 |
| 4. النص | `content_store.get_lessons_book` + `find_lesson` لكل درس · وللأحياء صفحات الوحدة |
| 5. التوليد | برومبت `quiz_gen` → **JSON صارم** · `temperature` منخفضة |
| 6. التحقق | 4 خيارات بالضبط · `correct_index` ضمن 0–3 · لا أسئلة مكرّرة · العدد مطابق · `lesson` من القائمة المطلوبة |
| 7. إعادة المحاولة | مرة واحدة عند فشل الـparsing (كما في v3) |
| 8. الموديل | **موديل المادة نفسه** (فيزياء→GPT-4o-mini · احياء→Gemini · رياضيات→DeepSeek) للحفاظ على مستوى اللغة |

**الأسئلة لا تُخزَّن إطلاقاً** ([03§5](03-data-strategy.md)) — تُولَّد وتُستهلك.
`prompts/quiz_gen` في Firestore لاحقاً مع اللوحة؛ الآن ثابت في `core/quiz.py` بنفس أسلوب برومبتاتك.

## 6. قاعدة البيانات — كتابة واحدة لكل اختبار

```jsonc
users/{uid}/results/{resultId}
{
  "type": "quiz",
  "subject": "فيزياء", "grade": 3, "track": "علمي",
  "unit": "الفيزياء الذرية", "lessons": ["نظرية بوهر"],
  "score": 7, "total": 10,
  "duration_sec": 214,
  "wrong": [                                  // ★ أدق من wrong_topics المسطّحة
    { "topic": "مستويات الطاقة", "lesson": "نظرية بوهر", "unit": "الفيزياء الذرية" }
  ],
  "created_at": "…"
}
```

> 🔑 **لماذا `wrong` كائنات لا نصوص؟** v3 اقترح `wrong_topics: [نص]`. لكن قسم التحليل يحتاج أن يقول: «ضعفك في **درس** نظرية بوهر» ويفتح **ذلك الدرس** في الشات. النص المجرّد لا يكفي لفتح الدرس — والحقل الإضافي مجاني الآن ومكلف لاحقاً (ترحيل).

**نفس نمط المحادثات ([28](28-auth-slice.md)):** Hive أولاً (فوري وأوفلاين) + نسخة سحابية fire-and-forget، **معزولة بالحساب** (`ownerUid`)، بلا مستمعين.

**قواعد الأمان:** `users/{uid}/results/{id}` مغطّاة أصلاً في `firestore.rules` — يُضاف تحقّق شكل مثل المحادثات.

**الكلفة:** اختبار = **كتابة واحدة**. طالب يختبر 3 مرات يومياً × 2,500 طالب = 7,500 كتابة — ضمن المجاني (20,000).

## 7. الوصل مع قسم التحليل 📊

```
اختبار → نتيجة محفوظة → التحليل يجمّع محلياً (بلا أي قراءة سحابية)
   ├─ لكل مادة: متوسط الدرجات · عدد الاختبارات · اتجاه التحسّن
   ├─ لكل درس : نسبة الخطأ  ⇒ «أضعف 3 دروس»
   └─ 🔁 الحلقة الذهبية: «اشرح لي 📚» → يفتح الشات على **نفس الدرس**
                          «اختبار مراجعة» → يولّد اختباراً من الدروس الضعيفة فقط
```

التحليل **لا يحتاج خادماً ولا قراءات Firestore** — يقرأ من Hive. وهذا يجعله فورياً ومجانياً.

## 8. مراحل التنفيذ

| # | المرحلة | المخرَج | اختبارات |
|---|---|---|---|
| 1 | `core/quiz.py` + `/quiz/generate` + التحقق الصارم | توليد يعمل على مادة حقيقية | صحة JSON · 4 خيارات · لا تكرار · مادة غير مقررة ⇒ 400 · صف بلا محتوى ⇒ رسالة · إعادة المحاولة |
| 2 | نموذج `QuizResult` (Hive + Firestore) + المزامنة | النتيجة تُحفظ وتُزامَن | العزل بالحساب · القص · الاستعادة |
| 3 | وصل شاشات الديمو ببيانات حقيقية | اختبار كامل من الإعداد للنتيجة | ويدجت: 3 دروس كحد أقصى · التصحيح · الحساب |
| 4 | `modesFor` محكومة بالقدرات + إخفاء الوزاري للأول والثاني | الأوضاع الصحيحة لكل صف | مصفوفة صف×مسار×مادة |
| 5 | قسم التحليل على النتائج الحقيقية + الحلقة الذهبية | «اشرح لي» يفتح الدرس الصحيح | التجميع · أضعف الدروس |

**المرحلتان 1 و2 مستقلتان تماماً** ⇒ يمكن تنفيذهما بالتوازي مع مراجعتك للواجهات.

## 11. 📱 فحص فعلي على المحاكي (قاعدة المالك)

> **القاعدة المعتمدة من اليوم:** أي قسم أو خاصية تُفحص في **iOS Simulator**
> بتدفّق كامل ولقطات شاشة قبل قول «جاهز». `analyze` و`test` و`build` لا تكفي.

### 🐛 العلّة التي كشفها الفحص — ولم يكشفها شيء آخر
**العَرَض:** ضغط «ابدأ الاختبار» ⇒ **شاشة بيضاء فارغة**، بلا أسئلة وبلا خطأ.

**السبب:** `QuizPlayScreen` **لم تكن تستمع للمتحكّم** إطلاقاً. كانت تُعيد البناء
عند الفشل فقط (`if (!ok) setState`)، فمسار **النجاح** يبقى على أول إطار:

1. `AnimatedBuilder(animation: controller)` يلفّ الجسم — كل تغيّر يُعيد البناء.
2. حارس أخير `_emptyGuard()`: أي حالة غير متوقّعة تعرض رسالة وزر إعادة — **لا بياض أبداً**.
3. حذف `setState` من أزرار اللعب (المتحكّم يُشعر بنفسه).

## 12. 🎲 انحياز موقع الإجابة — علّة ثانية كشفها الفحص

**العَرَض في لقطات الفحص:** الأسئلة 1 و2 و3 كانت إجابتها الصحيحة **في الخيار
الأول** — وهذا انحياز معروف في كل الموديلات، والطالب يكتشفه من ثالث اختبار
فيجيب بلا قراءة.

**لماذا لم يُصلحه البرومبت؟** طلبُ «نوّع المواقع» لا يجدي: الانحياز في أوزان
الموديل لا في فهمه للتعليمات.

**الحل — حسابي لا لغوي** (`quiz.spread_answers`):
- توزيع **متوازن لا عشوائي**: كل أربعة أسئلة تأخذ المواقع (٠،١،٢،٣) مرةً لكلٍّ
  بترتيب مخلوط. العشوائية المجرّدة قد تُخرج «أ أ أ أ» صدفةً — وهو عين ما نهرب منه.
- **تبديل (swap)** يحفظ الخيارات الأربعة كما ولّدها الموديل: لا حذف ولا إضافة،
  والخيار الصحيح يبقى نصّه هو هو، ويتغيّر موقعه فقط.
- ما بقي على البرومبت هو ما لا يصلحه الخلط: **تقارُب الخيارات في الطول والصياغة**
  — فالخيار الأطول يُكشف في أي موقع وُضع.

**قياس حيّ بعد الإصلاح (اختباران × 10 أسئلة):**
```
[0,1,2,3,1,0,3,2,1,0] → {0:3, 1:3, 2:2, 3:2}
[2,0,3,1,2,1,3,0,2,0] → {0:3, 1:2, 2:3, 3:2}
```
وفي المحاكي: سؤال الرياضيات الأول جاءت إجابته في **الخيار الثاني**.

### 🔇 وبديل الموديل الصامت أُزيل معه

**١. اختبار المراجعة كان يسقط دروساً من وحدات أخرى**

أضعف دروس الطالب موزّعة على وحدات بطبيعتها، وشاشة الإعداد كانت تقيّد الاختيار
بوحدة واحدة: `presetLessons` تُفلتر بـ`lessonsIn(_unit)` فيسقط الباقي **بصمت**،
وتغيير الوحدة من القائمة يمسح ما اختير.

| ما تغيّر | أين |
|---|---|
| الاختيار **تراكمي عبر الوحدات** — تصفّحُ وحدةٍ لا يمسحه | `quiz_setup_screen` |
| `_lessonUnit` تتذكّر وحدة كل درس مختار | `quiz_setup_screen` |
| شريط **«المختارة (n/3)»** بشرائح تحمل اسم الوحدة وزرّ إزالة | `_selectedLessons()` |
| `SubjectCapabilities.unitOfLesson()` — لإيجاد وحدة درسٍ مقترح | `subject_capabilities` |
| الإرسال بوحدة **أول درس مختار** | `_start()` |

> الخادم كان جاهزاً أصلاً: `collect_lessons_text` يبحث عن الدرس في وحدته
> ثم في الكتاب كله (`find_lesson(book, "", name)`) — فالعطل كان في العميل وحده.

**٢. ترتيب نقاط الضعف بعدد الأخطاء كان يظلم الطالب**

كلما اختبرت درساً أكثر تراكمت أخطاؤه فبقي متصدّراً وإن تحسّنت فيه — والمذاكرة
لا تُكافأ. صار الترتيب **بنسبة خطأ مرجّحة بالأحدث**:

```
w = 1, ½, ¼ …   (الأحدث أولاً)
النسبة = (Σ w·أخطاء + 1) / (Σ w·أسئلة + 2) × 100
```

| المكوّن | لماذا |
|---|---|
| **ترجيح الأحدث** | من ذاكر وأعاد الاختبار تنزل نسبته سريعاً ويخرج من القائمة |
| **تنعيم لابلاس** (`+1` و`+2`) | سؤالٌ واحد أخطأ فيه لا يصير «100٪ ضعف» ويتصدّر على درسٍ أخطأ فيه 8 من 10 |

**وهذا استلزم بيانات لم تكن تُحفظ:** `QuizResult.askedPerLesson` — كم سؤالاً جاء
من كل درس. بدونها نعرف الأخطاء ولا نعرف من كم سؤالاً، فلا نسبة أصلاً.
النتائج القديمة تصل فارغةً فتُقدَّر بقسمة الأسئلة على الدروس (`askedFor`).

⭐ وتُحتسب الآن **الدروس التي سُئل عنها ولم يُخطئ فيها** — بدونها لا تنزل نسبةُ
درسٍ أعاد الطالب اختباره ونجح فيه، فيبقى «ضعيفاً» ظلماً.

**الواجهة:** الشارة صارت `٦٠٪` بدل `✗9`، وورقة التفصيل تعرض النسبة والعيّنة
معاً («٣ من ١٠ سؤالاً») — الرقم المجرّد يُقرأ خطأً.

**الاختبارات:** 6 لنسبة الخطأ (الأكثر اختباراً لا يتصدّر · المذاكرة تُكافأ ·
عيّنة سؤالٍ واحد لا تتصدّر · نتائج قديمة لا تنهار) و3 لاختيار الدروس عبر
الوحدات — ضمن **138** اختباراً في التطبيق.

### 🔧 الجولة الثالثة من تعديلات المالك (2026-08-29)

**١. 🐛 «اشرح لي الدرس» لا يعمل في الرياضيات وحدها**

الرياضيات لها **آلة حالة منفصلة** في الشات، والفتح الموجَّه كان يملأ الأخرى:

| بقية المواد | الرياضيات |
|---|---|
| `selectedV3Unit` + `selectedV3Lesson` | `selectedMathBranch` + `selectedLesson` |
| `selectedMode` | `mathMode` |
| الدروس من `/content/capabilities` | الدروس من `/math/lessons?branch=` |

فتصل الشاشة وضعَ الشرح (لأن `mathMode` أصلاً `"شرح"`) ثم **تقف بلا درس** —
والطالب يضغط فلا يحدث شيء. أُضيفت `applyMathDeepLink` في `chat_controller`:
تضبط الفرع، تجلب دروسه، وتطابق الاسم؛ ولو لم تُطابق الوحدةُ مسحت بقية الفروع
(اسم الدرس لا يتكرّر بينها)، وإن لم يُوجد تُركت القائمة مفتوحةً بدل فرعٍ
مختارٍ بلا درس.

> 🐛 **والإصلاح الأول فشل — لأنه كُتب داخل شرطٍ لا يصحّ للرياضيات أصلاً:**
> `loadCapabilities()` تخرج مبكراً للرياضيات وتضع `caps = null`. فكلُّ ما
> عُشِّش تحت `caps?.lessonsAvailable == true` **كان شيفرةً ميتة** بالنسبة لها.
> الآن الرياضيات هي **الفرع الأول** من الشرط، خارج بوابة القدرات تماماً.
>
> 💡 ولماذا تخفّى العطل الأصلي؟ لأن الكيمياء والأحياء والفيزياء كلها تعمل —
> والمسار المكسور واحدٌ من بين ستة. **الحلقة الذهبية لم تكن مغلقة إلا في
> خمسة أسداس.**

**الاختبارات (4 في `math_deep_link_test`):** الوحدة الصحيحة تُثبّت بنداءٍ واحد ·
الوحدة الغائبة تُمسح الفروع لها · الدرس في فرعٍ آخر يُوجد · الدرس المعدوم لا
يترك فرعاً بلا درس. `applyMathDeepLink` صارت `@visibleForTesting` لأجلها.

**١-ب. والعلّة الحقيقية كانت في البيانات لا في العميل — «هندسة» و«جبر»**

بعد إصلاح العميل بقيت «هندسة» مكسورة و«تفاضل» تعمل. المحاكاة الشاملة (كل صف ·
كل مادة · كل درس) كشفت أن **لملف الدرس اسمين**، وأن كل مصدرٍ يسرد اسماً:

| المصدر | ماذا يسرد | يستعمله |
|---|---|---|
| `/content/capabilities` | `اسم_الدرس` **الداخلي** | بناء الاختبار |
| `/math/lessons` | **اسم الملف** | قائمة الشات |

```

| ملف **بلا امتداد `.json`** يسقط من القائمة ويظهر في القدرات | 1 («مبدأ العد») |
| ملفان باسمٍ داخليٍّ واحد ⇒ صفٌّ مكرّر | 1 (جبر) |

قديماً) وتتسامح مع الملفات بلا امتداد.

> 📐 **المحاكاة بعد الإصلاح:** ١٩٢ درساً في كل الصفوف والمواد — **صفر** ينكسر

**٢. ورقة نقطة الضعف: فعلان لا فعل واحد**

أُضيف **«إعادة الاختبار على هذا الدرس»** بجوار «اشرح لي» — في الشاشة العامة
وشاشة المادة. الشرح يعالج الضعف و**إعادة الاختبار تقيس هل زال**؛ وبدونها يبقى
الدرس ضعيفاً أبداً لأن نسبة الخطأ لا تنزل إلا بمحاولة جديدة. والعنوان صار
«الدروس التي تحتاج تركيز» — يقول ما هي بدل صفةٍ مبهمة.

**٣. التصنيف صار بنافذة آخر خمسة اختبارات مرجّحةً — لا بمتوسط العمر**

الفحص كشف أن نصفَي الشاشة يتناقضان: نقاط الضعف **مرجّحة بالأحدث** (الجولة
الثانية) فتقول «تحسّنت»، والتصنيف **تراكميّ مدى الحياة** فيقول «يحتاج تركيزاً».

> 🔑 **قرار المالك:** «مقياس المادة آخر خمسة اختبارات، والكفة الأرجح لآخرها،
> ولكن الأربعة البقية لهم حمل في النسبة».

الأوزان `1, ½, ¼, ⅛, 1/16` ⇒ الاختبار الأحدث يحمل **٥٢٪** من القرار والأربعة
الباقية **٤٨٪**. وما قبل الخامس لا يدخل الحساب إطلاقاً.

| السيناريو المقاس | التصنيف السابق | الآن |
|---|---|---|
| ٦ اختبارات بـ٣٠٪ ثم **١٠/١٠** | «يحتاج تركيزاً» ٤٠٪ | **«جيد» ٦٦٪** |
| أسبوع تحسّن ٤٠٪→٩٠٪ | «جيد» ٦٩٪ | **«جيد جداً» ٨٦٪** |
| ٤ اختبارات كاملة ثم **٣/١٠** | «ممتاز» ٨٦٪ | **«مقبول» ٦٤٪** |
| خمسة كاملة متتالية | «ممتاز» | **«ممتاز» ١٠٠٪** |

> ⚖️ **لماذا نافذة لا آخر اختبار وحده؟** لأن اختباراً واحداً حظُّه سيء (أو
> سهل) كان يقلب تصنيف المادة كلَّه. النافذة تجعل القلب **ممكناً لكن لا
> مجّانياً**: ١٠/١٠ بعد أربعة إخفاقات يقفز بك من ٣٠٪ إلى ٦٦٪ — تقدّمٌ يُرى،
> بلا ادّعاء أن الأربعة لم تكن.
>
> وهي **تُغني عن حارس عيّنة منفصل**: اختبار الخمسة أسئلة لا يقرّر وحده لأن
> الأربعة التي قبله باقيةٌ في الحساب (٤×٠٪ ثم ٥/٥ كامل ⇒ ٣٥٪ لا ١٠٠٪).

**أما خوف المالك من الدرس الذي نصيبه سؤالان** فمقيسٌ ومحلولٌ سلفاً:

```
درس أخطأ فيه ٤ من ١٠      → ضعفه ٤٢٪
ثم عاد بسؤالين صحيحين فقط  → ٣٣٪   (بقي في القائمة، ولم يقفز لـ«ممتاز»)
```
تنعيم لابلاس يسحب العيّنة الصغيرة نحو المنتصف. **ولا تقع الحالة على مستوى
المادة أصلاً** — الاختبار الواحد لمادة واحدة بخمسة أسئلة فأكثر، لا بسؤالين.

**`SubjectStats` صار برقمين:** `currentPercent` (نافذة الخمسة — عليه التصنيف
والحلقة وترتيب أفضل/أضعف مادة) و`percent` (متوسط السجلّ الكامل — يُعرض باسم
«متوسط سجلّك» فلا يُقرأ تصنيفاً).

**الاختبارات:** 7 للتصنيف بالنافذة (الأحدث أرجح لكنه لا يقرّر وحده · اختبارٌ
سيءٌ لا يهدم مادةً ممتازة · التحسّن يرفع · ما قبل الخامس لا يدخل · اختبار
الخمسة أسئلة محميّ · ترتيب المواد بالحالي) و4 للفتح الموجَّه للرياضيات —
ضمن **149** اختباراً.

### 🔍 مراجعة تشابك «اختبر نفسك» × «تحليل مستواي» (2026-08-29)

مراجعةٌ مقصودة للقسمين معاً بسيناريوهات قاسية. القسمان يتشابكان في ثلاث نقاط،
وكلٌّ منها كسر مرّة: (١) الاختبار يكتب `QuizResult` والتحليل يقرؤه · (٢) نقطة
الضعف تفتح الشات على (مادة · وحدة · درس) · (٣) «إعادة الاختبار» تفتح الإعداد.

**🐛 العلّة المكتشَفة — وحدةُ النتيجة تكذب في اختبار المراجعة**

اختبار المراجعة يجمع دروساً **من وحدات مختلفة** (قرار المالك، الجولة الثانية)،
لكن النتيجة تُختم بوحدةٍ واحدة — وحدة **أول درس مختار**:

```dart
..unit = _lessons.isEmpty ? _unit : (_lessonUnit[_lessons.first] ?? _unit)
```

و`WrongAnswer.unit` يأخذ وحدة الاختبار لا وحدة الدرس، فأخطاء الدروس الأخرى
**تحمل وحدةً ليست وحدتها**. ثم كان الفتح الموجَّه يقبل تلك الوحدة لمجرّد أنها
وحدةٌ **صالحة**، فيفشل شرط احتوائها للدرس ويصل الطالب وضعَ الدروس **بلا درس
مختار** — عطلُ الرياضيات نفسه، بسببٍ مختلف تماماً، وفي المواد الأخرى كلها.

**الإصلاح:** `resolveLessonUnit` — تُقبل الوحدة القادمة **فقط إن كانت تحوي
الدرس**، وإلا يُبحث عن الوحدة التي تحويه.

> ⚖️ ولمَ لم يُصلَح المنبع (ختم كل خطأ بوحدة درسه)؟ لأن `QuizQuestion` لا تحمل
> وحدة أصلاً، والخادم لا يرسلها. وحلّ الوجهة أمتن: يصحّ حتى مع النتائج
> **المحفوظة سلفاً** بوحدةٍ خاطئة، ومع أي نتيجةٍ تصل من السحابة.

**🐛 وثغرة ثانية:** الشاشة العامة لا تُمرّر `ownerUid` المحقون لشاشة المادة —
فتقرأ الأخيرة نتائج `UserSession` بدل الحساب المطلوب.

**ما فُحص ووُجد سليماً** (لا تغيير — الكود صحيح):

| المحور | النتيجة |
|---|---|
| شاشة الإعداد مع وحدةٍ خاطئة | ✅ تصحّح نفسها بـ`unitOfLesson` لكل درس |
| توليد الاختبار بثلاثة دروس من ثلاث وحدات | ✅ الثلاثة تُوجد (كيمياء · فيزياء · رياضيات) |
| وحدة وهمية | ✅ تُرفض برسالة عربية لا انهيار |
| الخروج من الاختبار في منتصفه | ✅ لا يُحفظ شيء — `saveResult` عند الإكمال فقط |
| استعادة نتيجةٍ من السحابة مرّتين | ✅ `put(r.id)` فلا تكرار، و`asked_per_lesson` يعبر الدورة |
| عزل الحسابات في المخزن | ✅ كل استعلام محكوم بالمالك |
| نتائج قديمة بلا `askedPerLesson` مع جديدة | ✅ تُقدَّر ولا تُفسد النسبة |
| اختبار وضع الوحدات (بلا أسماء دروس) | ✅ يُنسب للوحدة |
| اختباران في اللحظة نفسها · صفر أسئلة | ✅ لا قسمة على صفر ولا انهيار |
| مجموع أخطاء المفاهيم = أخطاء الدرس | ✅ دائماً |

**الاختبارات:** 17 في `quiz_analysis_integration_test` — ضمن **166** في التطبيق
و**252** في الخادم.

⚠️ **بندٌ للمالك (بيانات لا كود):** ملفان في «جبر» يحملان `اسم_الدرس` نفسه
