# 03 — استراتيجية البيانات: JSON أم Database؟ ⭐

## 1. الخلاصة

**السؤال مطروح بشكل خاطئ.** الصحيح:

> **قاعدة البيانات = مصدر الحقيقة للتحرير.**
> **الملفات = صيغة التقديم المُولَّدة.**
> **بينهما زر "نشر".**

## 2. لماذا لا تُنقل الدروس إلى Firestore

### (أ) الأداء — أبطأ بـ ~500 مرة
2.5 MB كلها ([11](11-content-schema.md#1)). JSON من الذاكرة ≈ 0.001 ms · Firestore = 50–300 ms **لكل مستند**. → [13](13-performance.md)

### (ب) FAISS — السبب الحاسم 🔴
الفهرس يُبنى من كل نصوص المادة. لو صارت في Firestore، كل إقلاع HF = آلاف القراءات. و**HF Spaces المجانية تنام وتُعاد كثيراً**. الطبقة المجانية 50,000 قراءة/يوم تُستهلك على إعادات التشغيل وحدها. → [13](13-performance.md#2)

### (ج) حد 1 MiB للمستند
وحدة أحياء كاملة قد تتجاوزه → تفتيت → عشرات القراءات لكل طلب.

### (د) لا بحث نصي
Firestore **لا يدعم البحث النصي الكامل**. البديل خدمة مدفوعة.

## 3. لماذا لا يكفي JSON الخام وحده
لا إضافة درس بدون نشر · لا تاريخ تعديلات · لا مسودات · لا تحقق صحة · لا تحرير من المتصفح.

## 4. 🏗️ الحل: خط أنابيب النشر

```
الأدمن يحرّر في اللوحة  →  Firestore: lessons_draft/{...}
                                   ⬇️ "نشر"
        POST /admin/content/publish {grade, subject}
          1. يقرأ الدروس من Firestore        [عند النشر فقط]
          2. يبني JSON بالصيغة الموحّدة       ← الصيغة 11§4
          3. يبني فهرس FAISS ويحفظه          ← يحل مشكلة 13§2
          4. يرفعهما إلى Firebase Storage
          5. يزيد content_version + hot reload
                                   ⬇️
        طلبات الطلاب من الذاكرة  →  صفر قراءات Firestore
```

**مكسب مزدوج:** خطوة النشر هي نفسها المكان الطبيعي لبناء فهارس FAISS مسبقاً — فتحل مشكلة الأداء الحقيقية ومشكلة إدارة المحتوى بضربة واحدة.

## 5. جدول القرار

| البيانات | التحرير | التقديم |
|---|---|---|
| المستخدمون والتوثيق | Firestore | Firestore |
| المحادثات · المحفوظات | Firestore | Hive |
| النتائج والإحصائيات | Firestore | Firestore |
| **محتوى الكتب (RAG)** | **Firestore (مسودات)** | **JSON + FAISS** |
| **بنك الوزاري** | Firestore أو ملفات | **JSON** |
| البرومبتات 🔒 | Firestore | Firestore + كاش 5 د |
| المنح · الخدمات · البانرات | Firestore | Firestore + كاش نسخة |
| اختبارات المواد | تُولَّد بالـ AI | لا تُخزَّن |
| الصور | Storage | Storage |

## 6. مطابقة اقتراح المالك
| اقتراحه | الحكم |
|---|---|
| تسجيل الدخول → DB | ✅ صحيح |
| محتوى التعليم → JSON | ✅ صحيح + طبقة تحرير |
| المنح → DB | ✅ صحيح |
| الاختبارات → JSON | ⚠️ مولّدة بالـ AI؛ النتائج → DB |

**«هل التغيير جذري؟»** لا — الصيغة المُولَّدة تبقى ملفات، والباك يقرأ ملفات. **نعم ومدمّر** لو قرأنا Firestore عند الطلب.

## 7. ماذا تفعل التطبيقات المشابهة
| المنصة | النمط |
|---|---|
| Khan Academy | CMS → حزم ثابتة على CDN |
| Duolingo | أداة تحرير → course bundles ثابتة |
| نجوى · Almentor | DB + CDN كثيف؛ الطلب لا يلمس الـ DB |
| Notion AI · Perplexity | مخزن محتوى + فهرس متجهات **يُبنى دورياً** |

**النمط الكوني: لا أحد يخدم محتوىً ثقيلاً من قاعدة بيانات مباشرة.**

## 8. Firebase أم Supabase؟
**التوصية: ابقَ على Firebase.** FCM وAuth ممتازان ومجانيان؛ v3 مبني حول قيود Firestore بذكاء؛ حجمك بعيد عن أي سقف.
**خط الرجعة:** كل وصول للبيانات خلف طبقة Repository.
