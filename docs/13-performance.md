# 13 — الأداء: أين يضيع الوقت فعلاً

> إجابة سؤال «هل الـ Database أسرع؟» — بالأرقام.

## 1. الجواب المختصر: **لا. أبطأ بـ ~500 مرة.**

| المصدر | زمن قراءة الدرس |
|---|---|
| JSON من ذاكرة العملية | **~0.001 ms** |
| JSON من قرص HF (مع page cache) | ~0.1 ms |
| **Firestore من HF إلى GCP** | **50–300 ms لكل مستند** |

وكل المحتوى **2.5 MB** ([11](11-content-schema.md#1)) — يدخل الذاكرة كاملاً. لا توجد مشكلة أداء يحلها الانتقال لقاعدة بيانات؛ الانتقال **يخلق** واحدة.

## 2. 🔴 أين المشكلة الحقيقية: بناء FAISS عند الطلب

```python
# Backend/subjects/common.py:197
async def faiss_search(texts, query, top_k=QA_TOP_K):
    fingerprint = md5(f"{len(texts)}_{texts[0][:80]}_{texts[-1][:80]}")[:16]
    if fingerprint not in _faiss_index_cache:          # ← كاش ذاكرة فقط
        async with get_build_semaphore():              # ← سيمافور = 2
            emb = embed_model.encode(texts, batch_size=32)   # 🔴 يبني الآن
            index = faiss.IndexFlatIP(...); index.add(emb)
            built = await asyncio.wait_for(..., timeout=40.0)  # 🔴 مهلة 40 ثانية
```

**ما يعنيه هذا عملياً:**

| الحقيقة | الأثر |
|---|---|
| الفهرس يُبنى **عند أول طلب** لكل (مادة، وحدة) | أول طالب يدفع ثمن البناء كاملاً |
| الفهرس **لا يُحفظ على القرص إطلاقاً** | كل إقلاع = بناء من الصفر لكل شيء |
| الكاش في الذاكرة فقط | HF Space ينام → الكاش يضيع |
| مهلة البناء **40 ثانية** | مكتوبة لأن البناء *فعلاً* قد يقارب ذلك |
| سيمافور = 2 | طالبان يبنيان بالتوازي، والثالث ينتظر في الطابور |
| البصمة = `len + أول 80 حرف + آخر 80 حرف` | ⚠️ **تصادم محتمل**: نصّان مختلفان بنفس الطول والحدود → فهرس خاطئ |

**السيناريو الواقعي:** الـ Space نام. الطالب يفتح التطبيق صباحاً ويسأل عن الأحياء → إقلاع Space + تحميل `paraphrase-multilingual-MiniLM-L12-v2` + بناء الفهرس + استدعاء الموديل. **الفرونت مهلته 60 ثانية فقط.**

> 🎯 **هنا يضيع وقتك — لا في قراءة JSON. ونقل الدروس إلى قاعدة بيانات يزيد هذا سوءاً**، لأنك تضيف قراءات شبكة **قبل** البناء البطيء أصلاً.

## 3. ✅ الإصلاح: بناء الفهارس مسبقاً

```
tools/build_indexes.py   (يُشغَّل عند النشر، ليس عند الطلب)
  لكل (grade, subject, unit):
      texts = extract_texts(book)
      emb   = embed_model.encode(texts)
      faiss.write_index(index, f"indexes/{grade}_{subject}_{unit}.faiss")
      json.dump(texts, f"indexes/{grade}_{subject}_{unit}_texts.json")
```
عند الإقلاع: `faiss.read_index(...)` — **تحميل ملف، لا حساب**. من عشرات الثواني إلى أجزاء من الثانية.

**مكسب إضافي:** الفهارس المبنية مسبقاً تُرفع إلى Firebase Storage، ولوحة التحكم تعيد بناءها عند نشر محتوى جديد — وهذا بالضبط خط أنابيب النشر في [03-data-strategy](03-data-strategy.md).

## 4. مشاكل أداء أخرى مرصودة

### (أ) `book.index` و`exam_embeddings.npz` ملفات ميتة
موجودة في المستودع، **لا يقرؤها أي سطر** (تحققت بـ grep على كل `.py`). بقايا محاولة سابقة لحفظ الفهرس — الفكرة كانت صحيحة لكنها هُجرت.

### (ب) الموديل يُحمَّل عند الاستيراد
```python
# common.py:15
embed_model = SentenceTransformer("paraphrase-multilingual-MiniLM-L12-v2")
```
سطر على مستوى الوحدة → يُحمَّل عند كل إقلاع (~470 MB تنزيلاً أول مرة، ثم ~90 MB في الذاكرة). يجب تثبيته في صورة Docker لا تنزيله وقت التشغيل.

### (ج) لا كاش للكتب
`load_json_safe` يُستدعى في كل طلب ويعيد تحليل JSON. صغير (2.5 MB) لكنه هدر مجاني — `@lru_cache` أو قاموس عام يكفي.

### (د) `QA_TOP_K = 3`
منخفض. مع الوسم الصحيح ([12](12-wazari-accuracy.md)) قد يستحق الرفع إلى 5.
